# TUI 与断线重连设计

> 基于 v1.14.2.13 运行时实测（`__netInst` 源码 + 状态机 + 多次会话观察）

---

## 一、先回答核心问题：断线要不要重新登录？

**大部分情况不需要，而且也不需要你提供任何登录信息。**

| 场景 | 需要重新登录吗 | 我的注入是否幸存 | 处置 |
|---|---|---|---|
| **WSS 网络抖动** | 游戏自动重连（自动重取 code） | **✓ 幸存** | 无需干预 |
| **请求超时** | 游戏自己处理 | **✓ 幸存** | 无需干预 |
| **服务端踢下线** | 游戏可能停止运行 | ✓ | 需重开游戏页 |
| **游戏页面刷新 / 重启** | 游戏自动重新登录 | **✗ 全部丢失** | **自动重抓（已实现）** |
| **微信客户端关闭** | 需要 | ✗ | **需人工重开** |
| **调试端口关闭** | 不需要 | ✓（仍在游戏内） | 重开端口 + 重连 CDP |
| **挂机脚本崩溃** | 不需要 | **✓ 幸存** | 重跑脚本即可 |

**结论：TUI 不需要账号密码、不需要 code。** 登录态始终由游戏客户端自己持有，脚本只是"搭便车"。

## 二、为什么网络抖动不影响注入（源码依据）

实测 `__netInst` 的关键实现：

```js
// 重连时新建 socket，但网络管理器实例本身不变
connect(url, cb) {
  this._connectCallback = cb;
  this._socket = new WebSocket(url);       // ← 只有 socket 换新
  this._socket.binaryType = 'arraybuffer';
  this.initSocket();
  this._state = STATE_INIT;
}

// 重连只是关闭旧 socket + 清理，不重建管理器
reconnect() {
  logger('重连 ' + this._url + ' 状态 ' + this._state);
  this.closeSocket();
  this.resetSocketState();
  Global[...] = ...;
}

// 重试上限 3 次
retryConnect() {
  if (this._state <= STATE_INIT) return true;
  if (!NetworkAvailable()) return true;
  if (!Enabled) return true;
  this._retryCount++;
  if (this._retryCount > this._maxRetryCount) {   // _maxRetryCount = 3
    logger('超过最大重试次数');
    return false;
  }
  this.reconnect();
  return true;
}

// 连接成功时清空在途请求表
onConnected(t) {
  this._state = STATE_CONNECTED;              // = 5
  this._waitMessageMap.clear();               // ★ 在途回调全部丢弃
  if (this._needReconnect) this.realReconnect();
  if (this._reconnectUrl) { this.connect(this._reconnectUrl); this._reconnectUrl = null; }
}
```

**三个关键推论**：

1. **`__netInst` 是长生命周期对象**，重连只换内部 `_socket` → 我注入的 `__bot`（持有 `__netInst` 引用）继续有效。
2. **`reconnect()` 里没有任何生成 code 的逻辑** → code 由**业务层**在重连时重新获取（`wx.login()`）。所以「断线要重新登录」这件事是**游戏自己完成的**，外部无感。
3. **`onConnected` 会 `_waitMessageMap.clear()`** → **断线瞬间在途的请求，回调永远不会被调用**。这是最需要防御的点。

## 三、三层自愈设计

```
┌ Layer 3  会话层（业务语义）
│  超时不重发 · 断线暂停 · 恢复后对账
├ Layer 2  桥接层（Bridge.ensure，已实现）
│  检测 __bot 存活 → 不可用则重连CDP → 重探上下文 → 重抓 __netInst → 重注入
└ Layer 1  游戏自身（网络层）
   抖动自动重连 · 自动重取 code · 最多重试 3 次
```

### Layer 1：交给游戏

不干预、不干扰。脚本只当旁观者。

### Layer 2：Bridge 自愈（`tools/core.mjs`）

```js
async ensure() {
  if (CDP 断开)            await this._dial();          // 重连调试端口
  if (!this.ctxId)         await this.detectContext();  // 重新探测游戏上下文
  const p = await this.ping();                          // typeof __bot 可用性
  if (p.ok) return p;                                   // 正常，直接返回
  // ---- 失效：完整重抓 ----
  this.recoveries++;
  await this.detectContext();
  await this.grabNetInst();     // 断点法重抓（最长等一次心跳 25s）
  await this.injectBot();
  return await this.ping();
}
```

触发时机：
- 所有任务开头的隐式前提
- 任务抛错且错误信息匹配 `/CDP|__bot|netInst|上下文/` → **自动 ensure 后不重试当前任务**（避免重复写操作）
- 用户按 `r` 手动触发

### Layer 3：会话层语义（TUI 已实现的部分 + 待补）

**已实现**
- 每个请求 15s 超时（`__bot.call` 内置），超时返回明确错误而非永久挂起
- 写操作**绝不自动重发**（`taskHarvest` / `taskPlant` 失败即上报，由下一轮 `AllLands` 对账）
- 业务错误码与网络错误分离（`err.code` vs 异常）
- 每日额度类错误（`1001046`）触发**当日熔断**，不再重复尝试

**待补**
- 断线期间**暂停任务队列**（监听 `_state != 5`）
- 恢复后用 `AllLands` **对账**，而不是凭记忆重试
- 长时间不可达时**退避重试**（30s → 60s → 120s）

## 四、TUI 使用

```bash

node tools/tui.mjs

# 跳过引导
node tools/tui.mjs --gid 1274359435

# 无界面单次执行（适合定时任务 / cron）
node tools/tui.mjs --once

# 常用参数
--port <n>    调试端口，默认 62000
--gid  <n>    自己的 gid，默认自动从心跳解析
--seed <n>    种植用的种子 ID，默认 20002
```

**引导只需要三项**（都可以回车用自动值）：

| 输入项 | 默认 | 说明 |
|---|---|---|
| 调试端口 | 62000 | First / 微信调试端口 |
| 自己的 gid | 自动探测 | 留空则从心跳体 field1 解出 |
| 种植种子 ID | 20002 | 白萝卜；种子不足会自动购买 |

**快捷键**

| 键 | 功能 |
|---|---|
| `/` | **进入指令模式**（Enter 执行 / Esc 取消 / ↑ 调出上次） |
| `h` | 一键收获（成熟地块） |
| `c` | 一键铲除（枯死植株） |
| `p` | 一键种植（自动铲除枯株 → 查种子 → 不足则购买 → 种下） |
| `d` | 一键务农（帮好友清理草虫，有奖励） |
| `f` | 刷新好友列表 |

| `i` | 一键撒虫（仅无虫地块） |
| `w` | 一键撒草（仅无草地块） |
| `a` | 挂机四件套：收获 → 种植 → 偷菜 → 务农 |
| `m` | 挂机开关（每 60s 执行四件套） |
| `r` | 强制刷新 + 桥接自愈 |
| `q` | 退出 |

### 指令模式（`/`）

**挂机的唯一前提是「登录成功」**——即调试端口可达、游戏处于已登录态（`_state=5`）。启动时 `Bridge.ensure()` 会自动完成：连接 CDP → 探测游戏上下文 → 抓取 `__netInst` → 注入适配层 → 解析 gid。就绪后即可挂机，**不需要额外的前置条件**（不必进主场景、不必先进某个页面）。

挂机只跑「**收获 → 种植 → 偷菜 → 务农**」四件事——它们**没有额度限制或额度充裕**，可无人值守反复执行。

**撒虫 / 撒草属于「放置」类操作**：有每日 100 次共享额度，且会打扰好友，因此**不进挂机循环**，由使用者按需主动执行。

按 `/` 进入指令模式，Enter 执行、Esc 取消、`↑` 调出上次指令。**指令支持中文**（英文别名同样可用）。

```
【挂机四件套｜无额度限制，可反复执行】
  /收获              收取成熟作物
  /种植 [种子ID]      自动补种空地（种子不足会自动购买）
  /偷菜 [gid]         偷取好友成熟果实（省略 gid = 全部好友）
  /务农              帮好友清除杂草与虫（有奖励，额度无限）

【自家操作】
  /铲除              清理枯死植株（收获后残留，不铲除无法补种）

【放置类｜每日 100 次共享额度，需指定好友 gid】
  /撒虫 <gid>         给好友地块放虫（仅对无虫地块生效）
  /撒草 <gid>         给好友地块放草（仅对无草地块生效）

【其他】
  /好友              列出好友 gid 与草虫/可偷状态（挑撒虫目标用）
  /全套              执行挂机四件套一次
  /挂机              开关自动挂机（每 60s 一轮四件套）
  /状态              查看桥接与账号状态
  /刷新              刷新数据并执行桥接自愈
  /退出              退出程序
```

> 务农只对**好友**的地生效，不会动自己种的地。

## 五、挂机完整闭环（实测一致）

```
① AllLands ──→ 分类地块
   ├─ MATURE(6)         → ② Harvest
   ├─ DEAD(7)           → ③ RemovePlant
   └─ 空 / 铲除后空地    → ④ 查背包 → 种子不足则 BuyGoods → Plant
                                     ↑
                              商店 shop_id=2，商品 id=15（种子20002，单价2金币）

⑤ 好友：GetAll 筛候选 → Enter 取地块 → PutInsects/PutWeeds/Harvest → Leave
```

**关键业务规则（全部实测确认）**

0. **主从地块（最容易踩的坑）**：`LandInfo.master_land_id`(13) / `slave_land_ids`(14) 描述主地从属关系。**副产地的作物是主地的影子，不能单独收获/铲除/种植**——对它操作会返回 `1001008 土地已种植`。
   ```
   地5  master=0   slaves=[1,6,2]   主地，副产地 1/6/2
   地1  master=5   (显示为空)        副产地
   地2  master=5   (显示为空)        副产地
   地6  master=5   (显示为空)        副产地
   ```
   正确做法：**只操作 `master_land_id === 0` 的主地**，副产用 `PlantItem.auto_slave=true` 自动跟随。
   注意副产地在 `AllLands` 里显示为「空」，若不排除会被误当成可种空地。

1. **`phases` 列表含未来阶段的预测** → 判断当前阶段必须取「最后一个 `begin_time <= now` 的条目」，直接取 `phases[last]` 会永远判定为成熟。
   ```
   刚种下： [ GERMINATION begin=已过 ] [ MATURE begin=未来 ]   ← 取 last 会误判成熟
   成熟后： [ MATURE begin=已过 ]                              ← 只剩一条
   ```
   正确字段：`plant.isRipe` / `plant.currentPhase`（已封装在 `farm.mjs`）。

2. **收获后地块变 `DEAD`（枯株），不是空地** → 必须 `RemovePlant` 才能补种（少了这步地会锁死）。

3. **`Plant` 每块地一个独立 `PlantItem`** → 一个 item 挂多块地返回 `1000020`。

4. **`PutInsects/PutWeeds` 每块地一次请求**，间隔 80–160ms。

5. **额度 `10003` 是放虫与放草共享的**（每次操作 +1，每日上限 100）→ **必须按「剩余额度 ÷ 好友数」动态分配到每个好友**，否则前几个好友就会把当日额度烧光。实测：一轮 13 个好友 × 3 块 = 39 次操作，即消耗 39 点；若用固定 6 块/人，一轮就是 78 点，一天只够跑一轮。
   额度对照：`10001` 收获 · `10003` 放虫放草共用 · `10004` 放虫计数 · `10015` 社交道具。

6. **种子 ID ≠ 植物 ID**（`20002` 种子 → `1020002` 白萝卜；白萝卜 `growSec=60` 即 60 秒成熟）。

7. **偷菜门控用好友摘要的 `steal_plant_num`（field 6）**，不能用 Visit 回包里 `PlantInfo.stealable`（field 16）——后者是作物品种属性，恒为 `true`。

8. **放虫/放草各占独立槽位，必须按「无虫/无草」筛选**（实测，此前我误判为"作物品种差异"）：
   - `PlantInfo.weed_owners`(12) 非空 = 该地块**已有草**
   - `PlantInfo.insect_owners`(13) 非空 = 该地块**已有虫**
   - **已有虫的地不能撒虫、已有草的地不能撒草**，服务端回 `1001037`（错误文案"成熟或枯萎阶段不能放虫子"**有误导性**，真实原因是槽位已占用）
   - 实测对比：小果 24 块中仅 7 块无虫、13 块无草；按槽位筛选后撒虫成功率从 `1/3` 提升到 `3/3`，整体 54% → 67%
   **想清掉已有的草/虫要用 `PlantService.Farming`（务农）**，而不是撒新的。见规则 9。

9. **务农 `Farming`（清除草虫，与「放置」互补）**：
   - 请求：`{land_ids=1(packed); host_gid=2; field_3=3; field_4=4}`
   - **`field_3`/`field_4` 必须显式编码**：自家 `0/0`，帮好友 `0/2`（不能依赖 proto3 默认省略）
   - **支持一次提交多块地**（不像 PutInsects/PutWeeds 必须逐块），效率高得多
   - **帮好友务农有奖励**：实测每块 `1101×10`，清 24 块得 240
   - **额度近乎无限**：`id10005`/`id10006`/`id10007` 上限 `999999999`，不像放虫放草卡在 100
   - **`1001057` 是 noop 信号**（"作物不需要务农"），不是错误 → 应作为收敛条件退出循环，不要抛异常
   - **服务端可清理项少于本地判定**：实测久亮候选 7 块仅清 1 条。本地按 `weed_owners`/`insect_owners` 判定只能粗筛，权威判定在服务端
   - **清理结果有显示延迟**：一轮后立即复查可能仍有残留，需多轮收敛（最多 3 轮）
   - 预筛策略：先用好友摘要 `weed_num`/`insect_num` 粗筛好友，避免对无草虫的好友做无谓 `Enter`

10. **主从地块也适用于好友农场** → 巡田时同样要跳过 `master_land_id != 0` 的副产地。

   错误码过滤策略：
   - `1001036` 单株次数上限 → 跳过该地块，继续
   - `1001037` 槽位已占用（或阶段不符） → 跳过该地块，继续
   - `1001046` 今日总次数上限 → **全局熔断当日动作**

9. **好友的地也有主从关系** → 巡田时同样要跳过 `master_land_id != 0` 的副产地。

10. **业务错误码与网络成功是两层** → `meta.err != 0` 时网络层仍返回成功。`Bridge.call` 默认对业务错误抛异常（`err.code`），否则「种子不足 / 作物未成熟」会被误判为成功。

## 六、待办

**断线期间暂停队列**：当前断线时任务会各自超时（各 15s），体验上是"卡一下"。应改为主动监听 `_state`，断开即挂起，恢复即续跑。

**恢复后对账**：写操作在断线窗口内状态未知，必须用 `AllLands` 重新拉取后再决策，不能凭内存状态推进。

**种子自动购买的价格校验**：当前直接按商店返回价下单。应加金币余额检查，避免金币不足时反复失败。

**多账号**：`Bridge` 已按账号隔离参数（port/gid），扩展为多实例即可，但 TUI 需要多面板。

**`Enter` 结果缓存**：巡田目前每个好友都 `Enter` 一次。可先用 `GetAll` 的 `plant` 摘要粗筛（注意有延迟，仅作候选过滤），减少 `Enter` 次数。
