## 三、核心接口契约

### 3.1 网关层（唯一出口）

```ts
// core/gateway/connection.ts
export interface Gateway {
  connect(code: string): Promise<void>;      // 一次性 code
  call<R>(req: RpcRequest): Promise<R>;      // 业务调用，永不阻塞心跳
  on(event: 'online' | 'kickout' | 'close' | 'notify', cb: (p: any) => void): void;
  close(reason?: string): void;
  state: 'idle' | 'connecting' | 'login' | 'online' | 'closing';
}

export interface RpcRequest {
  service: string;    // e.g. 'gamepb.plantpb.PlantService'
  method: string;     // e.g. 'Harvest'
  body: Uint8Array;   // 已序列化的 protobuf（未加密）
  priority?: 'critical' | 'normal' | 'low';   // critical 专用心跳/ACE
  timeoutMs?: number;                          // 默认 20000
  expectErrorCodes?: number[];                 // 白名单错误码，不算失败
}
```

### 3.2 业务层（4 个需求直接对应）

## 四、五个必须做对的技术点

### 4.1 加密与 seq：网关层独占

```
业务 body(pb) ──→ tsdk.encryptBuffer() ──→ 塞入 GateMessage.body
                                            ↓
GateMessage{meta, body, token} ──→ pb.encode ──→ ws.send()
```

- **加密只在此一处**，业务层拿不到也不该拿到加密句柄
- `client_seq` 从 1 单调递增，与 `pendingCallbacks` 配对；回包按 `server_seq` 收敛
- 超时**不盲目重发**（写类操作重发 = 重复收获/重复放虫），只做「超时→记不确定→下轮对账」

### 4.1.1 `Plant` 手工编码（唯一的例外）

`Plant` 在 proto 定义里**没有对应的 message 类型**，必须手写字段。实测字段布局：

```ts
// PlantRequest 实际结构
// { field_2: { item_id: <seedId>, land_ids: [packed int64] } }
function encodePlantRequest(seedId: number, landIds: number[]): Uint8Array {
  const w = protobuf.Writer.create();
  const item = w.uint32(18).fork();        // 0x12 = field 2, wire 2
  item.uint32(8).int64(seedId);            // 0x08 = field 1, varint → item_id
  const ids = item.uint32(18).fork();      // field 2, length-delimited
  for (const id of landIds) ids.int64(id); // packed repeated int64
  ids.ldelim();
  item.ldelim();
  return w.finish();
}
// 发送：sendMsgAsync('gamepb.plantpb.PlantService', 'Plant', encodePlantRequest(...))
```

注意 `land_ids` 是 **packed** 编码（连续 varint 无逐项 tag），漏掉 `ldelim()` 会导致整个包解析失败。

### 4.1.2 登录报文：字段存在性必须与官方一致

`LoginRequest` 走 `gamepb.userpb.UserService.Login`，且**登录必须走 critical 分道**（此时尚未 online，不受排队器约束）。

protobufjs 按「调用方是否赋值」决定字段是否上链，因此必须显式写出官方抓包中的全部字段，包括空值：

```ts
{
  sharer_id: 0, sharer_open_id: '',
  device_info: { client_version, sys_software: 'Windows' },
  share_cfg_id: 0,
  scene_id: '1234567',
  report_data: { callback:'', cd_extend_info:'', click_id:'', clue_token:'',
                 minigame_channel:'other-qq', minigame_platid:2, req_id:'', trackid:'' },
  extra: Buffer.alloc(0),
}
```

漏写空字段 → 字节数比官方少 → 服务端可能直接拒绝。

### 4.2 心跳与反作弊：独立分道，永不被业务饿死

队列按 4 个优先级分道，各自独立配额：

| 分道 | 用途 | 说明 |
|---|---|---|
| `critical` | Heartbeat / AntiData | 硬保证，业务洪峰也照常发 |
| `normal` | 用户点击触发的动作 | 前台 |
| `low` | 巡田 / 好友同步 | 后台，可被 normal 抢占 |
| `ace` | TSDK 定时上报 | 5s/25s/30s/150s 四档 |

判死策略（对齐实测）：`missCount >= 3 且 入站静默 > 30s` → 主动断开重连，不静默卡死。

### 4.3 限流：两级闸门

```ts
// 一级：令牌桶（速率）
const bucket = new TokenBucket({ rate: 8, burst: 16 });

// 二级：每日动作硬顶（熔断）
// 放虫/放草遇到 1001046 立即熔断当日该动作，剩余地块直接 skip，不发请求
```

**逐块操作必须减速**：放虫/放草每块一次请求，间隔 `80~160ms` 随机；施肥每块 `50ms`。

### 4.4 单飞合并 + 状态缓存

`AllLands` / `GetAll` 在 UI 刷新、巡田、任务执行中会被并发触发。用 single-flight：同 key 的并发请求合并为一次，避免把请求配额烧在重复拉取上。

土地快照带 `ripe_time_sec / weed_time_sec / insect_time_sec / dry_time_sec` 倒计时 → **预测下次成熟时刻**，定时器直接 sleep 到点，而不是每 10 秒盲轮询。

### 4.5 状态机与重连

```
idle → connecting → login(20s超时) → online
                                    ↓
                       heartbeat_timeout / ws_close / kickout
                                    ↓
                              reconnecting(退避)
                                    ↓
                      需要新 code（一次性！）→ connecting
```

**关键**：`code` 是一次性的，重连必须重新走 `login_buffer → code` 链路。因此 `login_buffer` 要持久化，且要处理过期（过期时回落到扫码）。

## 五、四个任务的数据流

### 需求 1：一键收获 + 种植

```
AllLands ──→ 解析每块地状态
   ├─ 成熟地块 → Harvest{land_ids:成熟集, is_all:true}
   ├─ 空地块   → 计数（查询空地块数）
   └─ 空地集   → Plant{item_id:种子, land_ids:空地集}
                    ↑
              种子选择：配置优先级列表 → 取背包中可用的第一种
```

产出：`{ harvested: n, empty: m, planted: m, seedUsed: id }`

### 需求 2：一键拜访 + 一键清理

```
GetAll ──→ game_friends[]
   ├─ 拜访：分批并发 Enter{host_gid, reason:2} → Leave
   │        并发度 3~5，每批 sleep，避免触发风控
   └─ 清理：按 last_active_time / level 过滤 → DelFriend{friend_gid}
            默认 dryRun 输出候选清单，确认后才真删
```

> `GetAllReply.game_friends[].plant` 已含 `steal_plant_num / dry_num / weed_num / insect_num`，**拜访前就能算出该去谁家**，不必盲进。

### 需求 3：一键撒虫 / 撒草 / 偷菜

```
GetAll ──→ 筛选目标（按 plant.weed_num/insect_num/steal_plant_num）
   └─ 逐个好友：
        Enter{host_gid, reason:2}
          ├─ 撒虫：PutInsects 逐块 × N   （80~160ms 间隔）
          ├─ 撒草：PutWeeds   逐块 × N
          └─ 偷菜：Harvest{host_gid, land_ids, is_all:true}
        Leave{host_gid}
```

熔断：任一 `PutInsects/PutWeeds` 返回 `1001046` → 当日该动作全局熔断，不再发请求。

### 需求 4：监控挂机

```
MonitorLoop（事件驱动，非盲轮询）
   ├─ 启动：AllLands + GetAll 建初态
   ├─ 定时：每 60s 轻量校准（low 分道）
   ├─ 预测：按 ripe_time_sec 计算最近成熟时刻 → sleep 到点触发
   └─ 触发：成熟 → 跑需求1；空闲 → 跑需求2/3（可配开关 + 间隔）
```

## 六、登录方案选型（★ 项目最大风险点）

`code` 只能通过下列四条路径之一获得，**没有第五条**。选错会直接卡死项目。

| 方案 | 原理 | 工程门槛 | 长期可用性 | 依赖 |
|---|---|---|---|---|
| **A. 客户端内取码** | 在 PC 微信/QQ 小游戏内运行时取出 `wx.login()` 的 code，喂给外部进程 | **低** | 中（需客户端在线） | 微信/QQ 客户端常驻 |
| **B. 复刻 mmtls 扫码** | 扫码 → `login_buffer` → 自实现 mmtls 握手换 code | **极高** | 高（脱离客户端） | 需重写 ECDH+AES-GCM+LZ4+私有记录层 |
| **C. NapCat（仅 QQ）** | 经 NapCat 框架调 `/api/qq/miniapp/code` 取 code，`appId=1112386029` | 中 | 高 | 需自建 NapCat 服务 |
| **D. 手工抓码** | 抓一个 code 填进配置 | 低 | **不可用** | code 一次性 |

**D 直接排除**：code 一次性且有效期极短，用完即废，无法支撑挂机。

**B 是最重的选项**：需要实现完整的微信 mmtls 私有协议（`shortcloud.weixin.com`，从 `aedns.weixin.qq.com` 取 IP/端口，ECDH `prime256v1` → HKDF-SHA256 派生 → AES-GCM 加解密 → LZ4 解压 → 自定义记录层 `REC=0xF103`）。这是一条独立的大工程，且随微信客户端升级会失效。

**建议路线：先 A 跑通全链路，再评估是否需要 B。**

理由：A 能让你在 1~2 天内验证「网关层 + 加密层 + 业务 RPC」全部打通，把真正的技术风险（`tsdk.wasm` 加密、seq 配对、心跳）先挤掉。等挂机跑通了，再决定要不要为「脱离客户端」这件事投入 B 的成本。反过来做，会在两个高风险项上同时卡住。

无论选哪条，`login_buffer`（方案 B）或 `code 获取通道`（方案 A/C）都必须封装成同一个接口：

```ts
// core/auth/code-source.ts
interface CodeSource {
  // 每次重连都要调用：code 一次性，不可缓存
  obtain(): Promise<string>;
  // 通道失效时（buffer 过期 / 客户端离线）的恢复动作
  refresh(): Promise<void>;
}
```

这样上层网关层不关心 code 从哪来，三条路线可替换。**这也是把登录与会话解耦的唯一正确切口。**

## 七、实施路线

| 阶段 | 目标 | 验收 |
|---|---|---|
| **P0** | 定登录方案（A/C 二选一），拿到可用的 `code` | 手工喂一个 code 能连上 WSS |
| **P1** | 从官方小游戏包提取 `tsdk.wasm`，跑通 `G()` 初始化与 `ba/ca` 往返 | 加解密自洽 |
| **P2** | 网关层：Login 报文 + seq 配对 + 心跳 25s + 判死重连 | 挂机 1 小时不掉线 |
| **P3** | `AllLands` + `GetAll` 拉通，落状态缓存 | 能打印土地/好友全量 |
| **P4** | 需求 1：一键收获 + 种植 + 空地块计数 | 实际收获/种下 |
| **P5** | 需求 2：一键拜访 + 清理 | 巡完全部好友 |
| **P6** | 需求 3：撒虫/撒草/偷菜 + 熔断 | 动作生效且不超限 |
| **P7** | 需求 4：监控挂机 + CLI 面板 | 无人值守跑通宵 |

**两个硬门槛，且必须先做**：

`code` 是第一个——没有它连 WSS 都建不起来，任何后续验证都无法进行。建议先手工抓一个 code 写死配置，把 P1~P3 全部跑通（code 在测试期间可能过期，重抓即可），最后再回来把 `CodeSource` 换成自动化实现。

`tsdk.wasm` 是第二个——没有它就发不出任何合法请求，且不存在纯手写加密的替代实现。wasm 从官方小游戏包解包获得（微信/QQ 客户端缓存目录下的游戏包，`1.14.2.x` 对应 `v3.9.0.179xxxxxxx`）。**注意版本必须与你实际客户端一致**，版本不符会导致初始化凭据校验失败。

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| `code` 一次性，重连必须重取 | 封装 `CodeSource.obtain()`，禁止缓存；A 方案需处理客户端离线 |
