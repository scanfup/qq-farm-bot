## 二、三问三答

### 问题 1：Cookie 分析 / 最小 CK

**这个游戏不依赖 Cookie 鉴权，业务通道是 WSS。** 抓包中 0 条 Cookie 并非丢包，是因为命中的全是 CDN 静态资源。

真实鉴权链路如下。**注意：以下内容来自参考实现源码，不是本 HAR 的实证**——本 HAR 中 20 个相关关键词（`login_buffer` / `yybadaccess` / `pcyyb` / `wss://` / `code=` / `oauth` …）命中数全为 **0**。

```
① 微信扫码 OAuth（PC 开放平台）
   open.weixin.qq.com/connect/qrconnect  →  cookie: openid + accesstoken
   ↓
② POST yybadaccess.3g.qq.com/pc_yyb_auth/pcyyb_get_wx_login_buffer_auth
   ↓  返回 login_buffer
   ↓
③ mmtls over TCP（非 HTTP！）
   shortcloud.weixin.com  ← 从 aedns.weixin.qq.com 取 IP/端口
   /ilink/ilinkapp/mp/wxaruntime_transfer
   ECDH prime256v1 + HKDF-SHA256 + AES-GCM + LZ4，记录层 REC=0xF103
   login_buffer + 游戏 appId → wx.login code
   ↓
④ wss://gate-obt.nqf.qq.com/prod/ws?platform&os&ver&code
```

**第 ③ 步是本项目最关键也最重的工程**：它不是 HTTP 请求，而是微信私有 mmtls 协议（`POST /mmtls/xxx HTTP/1.0` + `Upgrade: mmtls`，本质是 TCP 上的伪 HTTP 握手）。因此**任何 HAR / HTTP 抓包都不可能看到这一环**——WebInspector 只记录 XHR/fetch。

注意上表第二列：游戏 appId 在抓包里**只作为 referer 的 URL 路径存在，从不作为参数传递**。这就是「搜 `appid` 搜不到」的直接原因——搜的是字段名，而它是路径值。

### 官方小游戏自己怎么登录

`wx.login()` 是**客户端本地调用**，拿到的 code 通过 **WSS 的 Login 报文**发给游戏服务端（`gamepb.userpb.UserService.Login`，走 critical 分道）。

所以登录 code **存在于 WebSocket 帧中，不存在于 HTTP 层**。本 HAR 连一条 `websocket` 类型条目都没有，这一环同样抓不到。

**code 是一次性的**（且有效期极短），因此不存在「抓一次存起来长期用」的方案——每次重连都必须重新走 ①~③ 或重新取 code。这是架构上必须正视的约束。

**第二把锁**是每条网关消息里的 `gatepb.Message.token`，两种形态：
- 常规：`64 + randomInt(64)` 位字母数字，末尾追加 `=`，即 **65 ~ 128 字符**
- 账号绑定后，TSDK `H()` 会产生一次性初始化凭据：QQ 抓包实测 **152 字符 Base64 → 112 字节**，解码后长度 = `80 + openId字符数`，**只消费一次**（优先注入下一条编码完成的请求）

所以「最小 CK」的正确答案不是 cookie 串，而是：

```
核心：一次性 code（每次连接必需，不可缓存）
  ├─ 方案 B 才有：login_buffer（换取 code 的中间凭据，可复用直至过期）
  └─ 方案 A/C：code 由客户端/框架实时提供，无需自持凭据
配置：platform（qq|wx）/ clientVersion / gameId=3167
无用：Cookie、User-Agent 指纹（HTTP 层完全不参与游戏鉴权）
```

**注意**：`login_buffer` 只有走「方案 B（PC 扫码）」才存在。它不是这个游戏的固有概念，而是参考实现为了脱离微信客户端而自建通道的产物。若选方案 A（客户端内取码）或 C（NapCat），根本不需要它。选型见《02-架构设计》第六节。

### 问题 2：心跳保活

**存在，共两层，独立运行。**

**WS 应用层心跳**
- RPC：`HeartbeatRequest { gid, client_version }`
- 间隔：**25000 ms**（`CONFIG.heartbeatInterval`）
- 超时：单次请求有 `HEARTBEAT_REQUEST_TIMEOUT`
- 判死条件（`keepalive-policy.ts`）：`missCount >= 3` **且** 入站静默 `> 30000 ms`
- 触发后走 `finalizeConnection({source:'heartbeat_timeout'})` → 停机重连，而非静默卡死

**TSDK / ACE 反作弊保活**（登录成功后启动，违反会被踢）

| 周期 | 动作 |
|---|---|
| 5 s | `N()` 取待上报数据，非空则发 `AceService.AntiData` |
| 5 s | `P()` 处理已接收数据 |
| 25 s | `M()` 心跳 tick（负载只在此刻封装，比它更密的轮询只会拿到空） |
| 30 s | 速度外挂检测 `detectSpeedHack()` |
| 150 s | 上报 TSDK 状态 |

约束：同一账号**只允许一个 AntiData 请求在途**；服务端 `AntiDataReply.result` 非空时必须回灌 `O()`。实测 51 字节最小上报负载有固定字段布局与 FNV-1a 校验。

### 问题 3：接口参数是否加密

**是，双层封装，body 密文。**

```
GateMessage (protobuf 明文)
├── meta : { service_name, method_name, message_type=1,
│            client_seq, server_seq, error_code, error_message, metadata }
├── body : ★ 业务 protobuf → TSDK WASM 加密后的密文
└── token: 明文（65~128 字符 或 TSDK 一次性凭据）
```

关键点：**加密发生在 protobuf 字段内部，不是整帧加密**。`network.ts:367` 是唯一的加密入口：

```ts
if (finalBody.length > 0) finalBody = await cryptoWasm.encryptBuffer(finalBody);
```

TSDK WASM（`tsdk.wasm`，v3.9.0.1790160550 / 161,081 bytes）关键导出：`G` 初始化、`H` 一次性凭据、`M` 心跳、`N` 取上报数据、`O` 回灌、`P` 处理、`ba` 加密、`ca` 解密。

初始化顺序不可颠倒：先解密 mergewasm 元数据段 → `decrypt_all_data()` → `x()` → `G(gameId=3167, appKey=0)`。顺序错会触发 `table index is out of bounds`。

> 因此：**协议对接必须内置 tsdk.wasm，不存在纯手写加密的替代路径。**

## 五、抓包缺口与补抓清单

现有 HAR 不足以完成协议对接，需要补一次「实际操作阶段」抓包：
